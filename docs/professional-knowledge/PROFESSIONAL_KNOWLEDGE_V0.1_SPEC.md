# PersonalWorkspace · 专业知识模块 V0.1
## 产品、数据隔离、初始内容与开发规格（修订版）

**日期**：2026-11-07  
**状态**：规划完成，尚未实施。  
**替代范围**：替代《游戏研发知识库 V0.1 · 初始化配置与开发执行规格》中“继续使用原知识库页面、不新增专业主导航”以及“直接写入原有领域树”的建议。保留其 35 个游戏研发目录节点和 80 个候选知识主题，作为初始内容清单。

## 0. 决策

**产品上分开，技术上复用**：
- 原「知识库」继续用于个人收藏、灵感、项目记录、思维导图等。
- 新增一级导航「专业知识」，显示系统组织的概念、设计原则、方法、架构、工具及有证据的实践案例。
- **两者保存在同一个 `library.sqlite`**，共用原 `entries` 内容存储、稳定 UUID、历史、来源、关系、AI 审核、备份/恢复；专业知识通过独立的扩展表和独立分类树标识。
- 两者可以形成明确的引用或关联，但默认浏览、筛选、统计、搜索不混在一起。全站搜索如同时搜索两者，必须按空间标明来源。
- 现有内部 AI 是用户提问与管理的知识助手；外部项目 AI 自有项目上下文，仅需要目录、搜索、内容、关联四类只读能力。**不增设另一个需求理解 AI，不替外部 AI 重述项目需求，不把“何时查询”写进检索手册。**
- SQLite 继续作为正式知识数据源；**Markdown 导出不是必要条件**，可在以后作为可选互操作格式。

## 1. 内容身份与可信程度不得混淆

区分三件事：
1. **存放空间**：个人知识 vs 专业知识。这决定默认视图和编辑工作流。
2. **内容类别**：概念/原理、原则、方法/算法、架构/模式、工具/框架、实践案例。这是知识主题的性质，不等于权威级别。
3. **证据与审核**：来源属于官方文档、原始研究、专业书籍、开发者实践还是个人验证；内容是否已经核验、适用于什么技术/版本、何时最后核验。

不得仅凭“专业知识”身份就展示为“学术权威”或“已证实”。例如 Unreal GAS 属于特定引擎的框架；“属性修饰器”是更通用的概念；一个社区作者的实现经验可以被收录，但不能标成官方结论。

## 2. 页面设计

### 2.1 一级导航

`首页 | 任务台 | 收集箱 | 知识库 | 专业知识 | AI 助手`

- 原「知识库」仍按既有 UI 和个人领域树工作；默认查询排除专业知识条目。
- 新「专业知识」页面包含：左侧**专业领域目录树**、中间**领域概览/知识列表**、点击条目后的**阅读详情**。可继续复用现有搜索框、阅读器、来源/关系面板、编辑器、对话框等组件，但不沿用个人收藏的混合列表布局。
- 顶部全站搜索若跨两个空间查询，应给结果加清楚的“个人 / 专业”标识；不改变原知识库内部搜索的默认语义。

### 2.2 专业知识首页

- 当前所在领域名称、说明（回答“涵盖什么、不涵盖什么”）、子领域入口。
- 该领域的知识卡片列表；卡片突出标准名、中英文别名、类别、简短定义、证据/核验状态。
- 目录树展开/折叠、选择领域；支持从一级目录逐级深入；**空领域可以作为目录存在，但明确显示“尚未配置内容”，不制造假知识。**
- 搜索术语名称、别名、正文；可按类别筛选，默认采用目录顺序或概念顺序，而不是只有“最新更新”。
- 建立专业条目入口；编辑和删除继续沿用既有人工确认、草稿、回收站、历史保护。

### 2.3 专业条目详情

**必需展示**：规范名称（含英文名/别名）、类别、主要领域、核心定义、作用/解决的问题、适用与边界、来源与审核状态、相关知识。

**可选展示**：原理详解、代码实例、图示、适用引擎/平台/版本、常见误区、个人项目实践关联、最后核验日期。

不强制每个条目写教程或长文。不为每种类别开发不同的编辑器，沿用一个规范化的编辑表单和可折叠的正文区。

## 3. 数据方案（推荐方案，可在代码审计时做等价实现）

**明确分开“知识条目引擎”和“专业分类树”**：

- 继续使用 `entries` 存标题、简介、富文本正文与 `plain_text`；使用现有 UUID、`knowledge_records`（独立知识点）、版本、回收站、来源表和关系表。
- 新建 `professional_entries` 扩展表（以 `entry_id` 外键关联 `entries`），至少包含 `concept_kind`、`aliases_json`、`scope_note`、`seed_key`（可空、唯一）。不重复保存标题、正文、简介。
- 新建 `professional_domains`：独立专业树，包含 `id`、`parent_id`、`name`、`summary`、`scope_note`、`position`。树层级校验、防环、引用保护沿用或提取现有领域树验证函数。
- 新建 `professional_entry_domains`：一条知识可属于多个专业领域，但只标一个主要领域。验证主领域必须是已关联的领域。
- 如需要对来源增加“官方/原始论文/书籍/第三方实践”“适用版本”“最后核验日期”等专业审校元数据，新增轻量 `professional_source_reviews`（引用既有 `knowledge_sources` 的真实来源 ID），而不是复制来源正文。
- 专业条目可以通过现有 `knowledge_relations` / `relation_details` 引用个人记录，反向也可见，但双方内容身份保持不变。既有七类关系足以支持 V0.1；不强制新建图数据库。

**为什么不直接把专业目录继续写在 `domains`？** 该表目前包含个人知识领域，且名称全局唯一；如果共享，会污染个人领域树、造成同名限制和统计口径混合。新建一棵专业分类树只是在“分类”维度隔离，不是重做一整套知识存储、编辑或来源系统。

**必须贯穿改造的过滤点**：个人知识库主页和内容列表、个人领域数量、内部知识检索候选、回收站与搜索、全站搜索、专题动态成员、导入去重提示，以及外部 AI 专业知识 API。不要只在前端隐藏专业内容，服务端也需要明确的 scope 条件，避免错误统计或漏检。个人知识引用专业条目的合法性应保留。

**数据库迁移**：当前仓库知识 schema 11；若实施上述新表，建立顺序 schema 12 迁移，更新 `assertDatabaseSchema`、启动校验、完整工作空间 ZIP、旧备份向前恢复及相关测试。优先添加新表，不破坏旧表；测试只在隔离数据目录进行。不得因为开发方便覆盖用户现有数据。

## 4. 初始内容配置

### 4.1 第一个专业领域

`专业知识 → 游戏研发`（专业模块内的领域，**不写入个人领域树**）。

- 游戏研发根节点 1 个。
- 一级子领域 9 个：游戏设计与策划；软件设计与技术架构；游戏运行时与算法；图形渲染与视觉技术；美术、动画与音频；UI 与交互实现；数据、存档与网络；开发工具与工程化；测试、性能与发布。
- 二级目录 25 个，总计 **35 个目录节点**。二级节点名称及内容候选继承上一版初始化规格，实施时应针对正式环境的条目名称、分类术语与重复项审查，不要求死守名称。

### 4.2 知识主题

- **A 级 40 个**：需要编写经过具体来源核验、有意义摘要、正文和边界说明的专业知识卡；可以按小批次导入。
- **B 级 40 个**：作为待研究的种子清单，**不得**以空正文或伪“已核验”知识形式批量入库。
- 最先完成 10～12 张贯穿三个链条的样例：
  1. 角色控制器 → 碰撞体 / 刚体 / 射线检测 → Rapier；
  2. 高内聚低耦合 → 组件模式 / 事件驱动 / ECS；
  3. 属性修饰器 → Gameplay Effect → Unreal GAS（明确通用概念与引擎专有实现的区别）。
- 通过样例验收后再完善剩余 A 级 28～30 张。不能因为目标是 40 张，就用无来源的几句话凑数量。

### 4.3 资料与证据

- 优先官方技术文档、原始论文或标准、专业原著；其次高质量开发者实践。
- 以具体、直接支持该条结论的页面为来源，而不是仅把引擎官网首页挂在每一张卡片上。
- 只有真正核验过的内容才可标“已核验”；区分“来源是官方的”与“这条表述已核验”。
- 版权方面只存适量概述、原创归纳和链接，不批量复制整篇第三方文档。
- 初始来源参考：Robert Nystrom《Game Programming Patterns》官方全文目录、Rapier 官方角色控制指南、Unreal 官方 GAS 文档、Unity / Godot 官方文档等；对应术语必须逐条对照核验。

## 5. 初始化和编辑流程

1. **只读核对**：检查 `main/HEAD`、仓库状态、现有正式内容数量和实际分类，记录基线；任何修改先完整工作空间备份。
2. **结构迁移**：实施独立专业知识类型/领域树，验证旧库和新库同时正常、老知识不混入新模块。
3. **配置目录**：用版本化种子清单生成专业目录，先预览差异再确认创建；重复执行必须幂等、不能覆盖人工修改。
4. **先导入 10～12 张**：验证来源、类别、别名、关联、两个空间的显示与过滤。
5. **扩展到 A 级 40 张**：每批来源核验和差异审核通过才写入；B 级只留在待研究清单。
6. **内部 AI 适配**：在知识助手界面提供“个人知识 / 专业知识 / 两者”查询范围；默认由当前使用入口决定。人工管理操作仍有审核权限和明确确认。原有 API/凭据/费用策略不变。
7. **外部 AI 只读适配**：优先复用同一服务层的读取函数，按实际工具接入方式封装 MCP、CLI 或受控 API；不要求 Markdown 导出，也不要求外部 AI 先转述项目需求。
8. **测试和关闭**：构建、自动测试、真实浏览器两端回归、数据库升级/备份恢复验证、文档更新后再提交代码。

### 已有 JSON v2 导入的使用边界

仓库现有 `knowledge-exchange-v2.schema.json` 和 `import-v2.js` 已支持来源、专业知识可用的内容、关系候选及领域层级，但**它目前把领域写到旧的 `domains` 体系**。专业模块的导入应复用其安全解析、审核、事务和来源存储机制，同时新增“目标为专业知识”的写入路径。不能直接用旧 v2 导入把 35 个专业目录写回个人领域树，也不能把导入时的关系候选自动变成确认事实。

## 6. AI 的两个入口

### 内部 AI（网站内）
- 用户提问，例如“Rapier 和 Character Controller 有什么关系？”
- 由当前范围检索个人、专业或二者的相关知识；可以引用真实来源及状态。
- 知识管理员可以提出增删、修正、补充等建议，实际改变正式知识要经人工审核。
- 不为它开发第二个 AI 模型或第二套知识存储。

### 外部项目 AI（Codex / Cline）
- 由它根据已经存在的项目上下文决定自己检索什么，并组织搜索词。
- 知识库只需提供以下四类只读能力：
  - `list_professional_domains(parent_id?)`：领域树、范围说明、子类及数量；
  - `search_professional_knowledge(query, domain_id?, kind?)`：稳定 ID、名称、别名、简介、匹配信息；
  - `read_professional_knowledge(id)`：正文、来源、审核状态、适用范围、版本；
  - `get_professional_related(id)`：相关专业知识及明确跨到个人知识的引用（关系/方向/状态）。
- 提供 `README` / 初始资源作为**检索使用手册**，提供领域树作为**检索地图**；不写“什么时候应该搜索”，不写固定技术决策 SOP，不上传或复制外部项目上下文。
- 外部接口默认只读、最小权限，只提供被授权的内容空间，不因为是 localhost 就绕开现有访问安全设计。

## 7. 需要交付的真实界面

1. **专业知识首页**：独立导航、专业目录树、领域概览、卡片列表、搜索、类别筛选。
2. **专业知识阅读页**：规范名称、别名、类别、核心定义/用途/边界、正文、来源、相关知识、人工编辑入口。
3. **专业知识管理/导入**：目录增删改/排序、知识草稿审核、批量初始化预览、来源审校状态。第一版可复用原有 Dialog 和编辑器，不重做整个设计系统。
4. **内部 AI 助手的范围选择**：让个人资料和专业知识能够被单独检索或明确组合。

初版不做：独立新网站、第二套备份引擎、大型自由知识图谱、强制嵌入模型/向量数据库、全自动网页抓取、无人监督的批量知识生成、外部 AI 写入权限、学习打卡/熟悉度打分、手机访问功能。

## 8. 核心验收

| 验收项 | 通过条件 |
|---|---|
| 个人与专业隔离 | 原知识库默认列表/分类/统计不出现专业卡；专业模块不混入个人笔记 |
| 同源复用 | 每条专业知识仍使用现有 `entries` UUID、正文、来源与版本机制 |
| 内容分类 | 游戏研发 35 目录正确可导航；分类不污染个人领域树 |
| 内容质量 | 先完成 10～12 条样例验证，再达到 A 级 40 条；B 级待研究不伪装成正式知识 |
| 人类阅读 | 既能从目录找到知识，也能通过别名、关联及搜索找到概念 |
| 内部 AI | 个人/专业/全部范围有明确过滤，回答引用真实内容，写入需审核 |
| 外部 AI | 不复制项目需求，通过目录、搜索、阅读、关联四步找到所需知识；能区分相关概念与具体框架 |
| 交叉引用 | 专业概念可指向个人实践；两者仍在各自空间显示 |
| 安全与回归 | 无数据覆盖、重复初始化幂等；完整备份恢复通过；`npm run build`、`npm test` 和真实浏览器回归通过 |

## 9. 开发包划分

- **D1 结构和页面**：专业身份与目录模型、schema 迁移、导航与两种视图隔离。
- **D2 内容种子与审校**：35 目录、12 样例专业条目、内容审核、导入链、补齐 A 级 40。
- **D3 AI 调用**：内部知识助手的空间范围，外部只读知识工具，检索手册与地图。
- **D4 回归与交付**：自动测试、真实 UI、备份恢复、最终文档和 Git 提交。
